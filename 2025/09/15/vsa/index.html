Vertical Slice Architecture

發表於 2025-09-15 更新於 2026-10-09 分類於 軟體設計
以業務功能為中心重組程式碼，透過垂直切片架構（VSA）提升可維護性與開發效率，並附上 C# + MediatR + Minimal API 的實作範例。

前言：為何需要新的架構思維？

在傳統的軟體開發中，我們習慣於「水平分層」架構（Layered Architecture），將程式碼按技術職責劃分，例如 Controllers、Services、Repositories。當要新增一個功能時，你可能需要在這三個資料夾中各新增或修改一個檔案。這種做法雖然清晰地分離了技術關注點，但在功能變得複雜時，卻會導致程式碼高度分散：修改一個小功能就得在專案各處「跳來跳去」，心智負擔極高。

「垂直切片架構」（Vertical Slice Architecture，VSA）提供了截然不同的解法：以「業務功能」為中心組織程式碼，將處理單一請求所需的所有邏輯封裝在一起，形成一個獨立、內聚的「切片」。

什麼是垂直切片架構（Vertical Slice Architecture）

圖解理解（概念示意）

試著這樣理解：傳統分層架構就像按書籍尺寸或顏色整理整座圖書館；而垂直切片則是按主題分類。當你想找「歷史」，你不會想把整個圖書館翻過一遍，而是希望所有歷史書都集中在同一區域。

圖：傳統分層把相同「技術型別」放一起，查找需跨區域奔波；垂直切片把同一「業務主題」放一起，定位更快。

垂直切片架構的核心思想是：把與單一功能相關的所有程式碼（從 API 端點到資料存取）放在同一個地方。每個「切片」都是自給自足的單元，獨立處理一個請求並返回結果。

核心概念

  • 功能導向組織（Feature-Oriented）：不再依技術分層（Controllers、Services），而是依功能分組（例如 Features/ExportUserData、Features/CreateOrder）。
  • 高內聚、低耦合（High Cohesion, Low Coupling）：切片內部包含完成任務所需的一切；切片之間保持鬆耦合，一個功能的變更不會輕易影響到另一個功能。
  • 自給自足的切片（Self‑Contained Slices）：減少在多個技術層資料夾間切換的認知成本。

傳統架構 vs. 垂直切片架構

以下透過檔案結構對比兩種做法。

傳統分層架構：一個「匯出使用者資料」功能，程式碼散落在各處。

📁 Controllers/
└── UsersController.cs       # 包含匯出功能的 API 端點
📁 Services/
├── IDataExportService.cs    # 抽象層
├── DataExportService.cs     # 實作各種服務的組合
├── ICloudStorageService.cs
├── CloudStorageService.cs
├── IEmailService.cs
└── EmailService.cs
📁 Models/
├── ExportDataRequest.cs
└── ExportDataResponse.cs
📁 Repositories/
├── IUserRepository.cs
└── UserRepository.cs

垂直切片架構：所有與「匯出使用者資料」相關的邏輯，都集中在一個資料夾內。

📁 src/
 ├─ 📁 Infrastructure/              # 存放真正跨切片共用的基礎設施服務
 │  ├─ ICloudStorageClient.cs
 │  └─ IEmailSender.cs
 └─ 📁 Features/
    └─ 📁 Users/
       ├─ 📁 ExportData/            # 這就是一個「垂直切片」
       │  ├─ ExportUserData.cs      # 請求、回應、處理邏輯、驗證
       │  └─ ExportUserDataEndpoint.cs # API 端點定義
       ├─ 📁 Create/
       │  └─ CreateUser.cs
       └─ 📁 GetById/
          └─ GetUserById.cs

說明：ExportData 資料夾包含該功能的所有程式碼。像 ICloudStorageClient 與 IEmailSender 這種真正通用的基礎設施服務，仍應抽象在 Infrastructure/ 並以依賴注入供各切片使用，避免重複與錯誤抽象。

程式碼範例：一個完整的切片

在 C# 實踐中，VSA 常與 MediatR 與 Minimal API 搭配，讓程式碼更精簡、關注點更單純。

Features/Users/ExportData/ExportUserData.cs

// 使用靜態類別作為命名空間，將所有相關型別組織在一起
public static class ExportUserData
{
    // 1) 定義輸入 (Request/Command)
    public record Request(Guid UserId) : IRequest<Response>;

    // 2) 定義輸出 (Response/Result)
    public record Response(string DownloadUrl, DateTime ExpiresAt);

    // 3) 處理器 (Handler)：封裝業務邏輯與外部互動
    public class Handler(
        AppDbContext dbContext,
        ICloudStorageClient storageClient,
        IEmailSender emailSender)
        : IRequestHandler<Request, Response>
    {
        public async Task<Response> Handle(Request request, CancellationToken ct = default)
        {
            // A. 查詢資料
            var user = await dbContext.Users
                .Include(u => u.Orders)
                .Include(u => u.Preferences)
                .FirstOrDefaultAsync(u => u.Id == request.UserId, ct);

            if (user is null)
            {
                throw new NotFoundException($"User {request.UserId} not found");
            }

            // B. 組裝匯出內容
            var exportData = new
            {
                user.Email,
                user.Name,
                user.CreatedAt,
                Orders = user.Orders.Select(o => new { o.Id, o.Total, o.Date }),
                user.Preferences
            };

            // C. 上傳至雲端並取得下載連結
            var fileName = $"user-data-{user.Id}-{DateTime.UtcNow:yyyyMMdd}.json";
            var expiresAtUtc = DateTime.UtcNow.AddDays(7);

            var downloadUrl = await storageClient.UploadAsJsonAsync(
                fileName,
                exportData,
                expiresAtUtc,
                ct);

            // D. 通知使用者（寄送含下載連結的 Email）
            await emailSender.SendDataExportEmailAsync(user.Email, downloadUrl, ct);

            return new Response(downloadUrl, expiresAtUtc);
        }
    }

    // 4) 驗證器 (FluentValidation)
    public sealed class Validator : AbstractValidator<Request>
    {
        public Validator()
        {
            RuleFor(r => r.UserId).NotEmpty();
        }
    }
}

Minimal API 端點：

public static class ExportUserDataEndpoint
{
    public static void Map(IEndpointRouteBuilder app)
    {
        app.MapPost("/users/{userId}/export", async (
            Guid userId,
            ISender sender) =>
        {
            var response = await sender.Send(new ExportUserData.Request(userId));
            return Results.Ok(response);
        })
        .WithName("ExportUserData")
        .WithSummary("Export user data and return a temporary download URL")
        .Produces<ExportUserData.Response>();
    }
}

端點職責單純：接收請求、轉送處理、回傳結果。也可將端點與處理器合檔，視團隊習慣而定。

檔案組織策略：單檔 vs. 多檔

  • 單檔優先：將請求、回應、處理器與驗證置於同一檔案，閱讀路徑最短、定位最快。
  • 適時拆分：當檔案超過 ~300–400 行、驗證或流程特別複雜時，再拆成多檔，但仍共置於同一資料夾。
  • 混合使用：專案層級不必強制一致，依功能複雜度彈性選擇。

架構優勢對比

面向 傳統分層 垂直切片
程式碼組織 依技術職責分層 依業務功能切片
修改功能 需於多個資料夾修改 變更集中於單一切片
心智負擔 高：需記住跨層關聯 低：相關邏輯共置
可演進性 較差：全域抽象（如 IBaseService）限制靈活性 佳：每個切片可獨立演進，甚至採不同處理模式
測試 倚賴較多整合測試，單元測試困難 切片級單元/端點測試容易
耦合性 層與層之間容易產生緊密耦合 切片間預設低耦合，共享僅限基礎設施

如何開始落地？最小化步驟

  1. 從新功能開始：在現有專案中，所有新功能改採 VSA。
  2. 順手重構：維護舊功能時，把相關類別與邏輯收攏到對應切片。
  3. 識別並保留真正的共享：認證、日誌、雲端儲存、郵件發送等放在 Infrastructure，以抽象介面 + DI 暴露。
  4. 端點靠近邏輯：使用 Minimal API 或將 Controller 共置於功能資料夾內。
  5. 語意化命名：以網域 + 動詞導向，如 Features/Orders/PlaceOrder、Features/Products/GetProductDetail。

常見誤解

  • 「這會違反 DRY 原則」
    迷思。適度重複優於錯誤抽象。若兩個功能的變更原因不同，強行抽象共享將造成未來耦合與維護災難。只共享穩定的基礎設施，而非業務邏輯。

  • 「這只是改變資料夾結構」
    不只是如此。它改變了思考單位與變更邊界：從「技術層」轉為「功能流」，直接降低讀寫與修改成本。

  • 「一定要用 MediatR 嗎？」
    非必需，但相當推薦。MediatR 提供優雅的請求/回應管線，可無痛插入驗證、記錄、快取等橫切關注點，並讓端點與處理器自然解耦。

結語

垂直切片架構不是銀彈，卻能實際解決傳統分層在複雜系統中的常見痛點。當你下次接到需求時，別再想「要在哪個 Service 新增方法？」而是問自己：「我要建立什麼樣的切片來完成這個功能？」這個思維轉換，將為專案帶來更高的清晰度與生產力。
